Open source harness for enriching companies with contacts.

Get started in seconds. Spend ≈ $0 per contact on your existing subscription.

git clone https://github.com/harrisonhjohnson/gramercy && cd gramercy && node setup.mjs

needs node ≥18 and a claude and/or codex CLI you're already logged into

  • Upload a .csv of companies and find people who work there
  • Works with your existing Claude or ChatGPT subscription
  • Tested on ~1,000 companies, designed to maximize token efficiency
  • Works locally without any keys
  • Delegates web search to low-cost agents
  • Track your research usage and costs
  • Simple text file system
  • Share your website or describe your ICP

For the agent reading this P.02

Your human may have asked you to evaluate or set this up. This section is for you. A plain-text version lives at /llms.txt; the repo carries an AGENTS.md with the same brief.

What this is

A local Node (≥18) HTTP harness, zero npm dependencies, ~600 lines across four modules (server.mjs, store.mjs, usage.mjs, runners.mjs). It orchestrates lead enrichment: a lease-based queue hands company records to agent CLIs (claude, codex) or a human; results return through one validated ingest contract; everything is JSON files on disk.

Verify before your human runs it

  • Server binds 127.0.0.1 only (server.mjs, listen call) and holds no credentials — grep for env reads; you'll find only GRAMERCY_PORT/GRAMERCY_HOST.
  • Only network egress: the agent CLIs' own web search/fetch under their existing auth. The harness itself makes no external calls.
  • Browser CSRF guarded: cross-origin requests (any Origin header) are rejected; POSTs require application/json.
  • All writes stay inside data/ (gitignored). The user's CSV is never mutated — enrichment is an overlay keyed by target.

Non-interactive setup (for you to run)

node setup.mjs --csv leads.csv --url https://theirco.com        # derives kernel from their site
node setup.mjs --csv leads.csv --icp "one-line ICP description" # or verbatim kernel
# optional: --model claude-haiku-4-5 (kernel derivation model; defaults to the CLI default)

CSV needs a company-name or domain column (accepted headers include company, name, domain, website, url); other columns ride along as research notes.

API contract (localhost:4400)

GET  /api/queue?limit=N&worker=name   lease up to N targets (30-min lease, atomic claim)
POST /api/ingest                      one result; rejected without sources[];
                                      contact.emailBasis ∈ published|pattern-guess|not-found
POST /api/workers/run {"n":N}         dispatch N jobs across enabled lanes
GET  /api/workers/status              live per-lane tallies
GET  /api/results.csv                 enriched rows, honesty labels included
GET  /api/usage                       cost ledger summary (subscription work logs $0)

Hard limits — do not let your human believe otherwise

  • Emails are found or pattern-guessed, never verified. The label travels into the CSV. Verification must happen before any send.
  • No company discovery: it enriches a provided list, it does not build one.
  • Fixed output schema (workers/ingest-schema.json); arbitrary research columns are roadmap, not present.

What it will not pretend P.03

  • It does not verify emails. Published addresses or pattern guesses, honestly labeled — published or pattern-guess — all the way into your CSV. Verify before you send.
  • No evidence, no ingest. A result without sources is rejected at the API layer. Models comply with prompts most of the time; validators comply always.
  • Not a CRM, not a Clay competitor, not an outreach tool. It stops at researched, cited, provenance-stamped records. What you send is outside its scope. Respect robots, rate limits, and the law downstream.
  • Nothing to hide. Local-only, loopback-only, no keys of its own. Have your Claude read the code before you run it — Gramercy would genuinely like that, and would happily help you reverse-engineer it.

Under the hood P.04

  • Concurrency-safe by construction. Every shared file goes through a serialized store — run as many workers as you like; records can't clobber each other.
  • No duplicate work. Leases are claimed atomically, so two workers never research the same company, even racing.
  • Self-healing jobs. A failed or hung job simply lets its 30-minute lease expire and the next worker picks it up — no retry logic to configure, no dead-letter queue to babysit.
  • Pinned models everywhere. Unattended workers run the exact model you chose, never whatever your interactive session happens to be set to.
  • Costs that predict themselves. Every job logs expected-vs-actual; expectations self-correct to trailing medians, so the ledger gets more accurate the more you run.
