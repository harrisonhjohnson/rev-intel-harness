*** JOB: ENRICH *** TARGETS: ~1,000 MARGINAL CASH: SINGLE-DIGIT $ LICENSE: MIT

A lease-based enrichment queue that treats coding agents — Claude Code, Codex, or you pasting into a chat UI — as interchangeable revenue-intelligence workers behind one evidence-gated ingest contract, with per-source provenance and an honest cost ledger.

Contact enrichment is a research task, and research is what agentic CLIs are quietly excellent at. Vendors price enrichment per row; raw API calls with web search cost real money at volume. The harness routes the work to agent subscriptions you already pay for — and meters everything, so you know it's actually cheaper.

Read the code on GitHub Run it in five minutes

How a run reads P.01

No database, no framework, no queue service. Three ~150-line Node modules, JSON files, curl. Every lane pulls from the same queue and posts to the same ingest endpoint — so swapping agent runtimes is a config change, and a human with a chat tab is a first-class worker.

$ curl -s "localhost:4400/api/queue?limit=1&worker=claude-code"
{ "rows": [ { "key": "glowlab", "domain": "glowlab.example.com" } ] }
# … agent researches the company on the open web …
$ curl -s -X POST localhost:4400/api/ingest -d @result.json
{ "error": "sources[] is required — no evidence, no ingest." }
$ curl -s -X POST localhost:4400/api/ingest -d @result-with-sources.json
{ "ok": true, "key": "glowlab" }
$ tail -1 data/usage-ledger.jsonl
{ "site": "enrich", "source": "claude-code", "actual": { "usd": 0 }, "ok": true }

Three lanes, one contract P.02

LaneRuntimeMarginal cost

Leases last 30 minutes and free themselves; a failed job needs no retry logic — the next worker simply picks it up.

Decisions that earned their place P.03

Extracted from a real GTM engagement, where it enriched ~1,000 companies — researched contact, firmographics, a specific outreach hook, cited sources — for single-digit dollars of marginal cash. Most of these rules come from getting burned:

  • No evidence, no ingest. sources[] is enforced at the API layer, not the prompt layer. Models comply with prompts most of the time; validators comply always.
  • Email honesty is a type. published | pattern-guess | not-found lives in the schema, so a guess can never masquerade as a verified address downstream.
  • The claim happens inside the mutex. The free-list comes from a stale read; check-and-set runs inside the serialized store, or two workers enrich the same company. This happened.
  • Enrichment is an overlay. Results never mutate the target list; provenance — which lane, which model, when — rides on every record.
  • The meter is a feature. Every unit of work lands in an append-only ledger with expected-vs-actual cost. Subscription work logs at $0, so cash spend and free spend sit side by side.
  • Pin models in unattended runs. A scheduled worker never inherits an interactive session's model choice.

Run it P.04

Bring your own agents — a Claude Code and/or Codex CLI, logged in on whatever plan or key you have. The harness itself calls no APIs and holds no keys, and it binds to loopback only.

$ git clone https://github.com/harrisonhjohnson/rev-intel-harness && cd rev-intel-harness
$ cp data/targets.sample.json data/targets.json   # then edit: your companies
$ $EDITOR workers/enrich-prompt.md                # aim the hooks at your ICP
$ node server.mjs
$ curl -s -X POST localhost:4400/api/workers/run -H "content-type: application/json" -d '{"n":4}'
$ curl -s localhost:4400/api/results | jq '.rows[] | select(.enrichment)'

It stops at researched, cited, provenance-stamped records — deliberately. What you send, and whether a pattern-guess email ever gets used unverified, is outside its scope. Respect robots, rate limits, and the law downstream.
